# ADR-0002: Project-scoped Kette instances, plugins per project

- **Status:** proposed (defaults of the session and the decisions of fix round 1, Alex may veto each)
- **Date:** 2026-10-31
- **Refs:** Workbase ZERO-538 (KD-0038), [docs/instances.md](../instances.md), `src/instance/`, `src/project-plugins.mjs`, `src/marketplace.mjs`, `test/sandbox.test.mjs`

## Context
Alex: "köennen wir mehrere gescopte kette-enteprsie oder kette-community instanzen erstellen? im prinzip projektbasiert mit eigenem projektscope?" and "user kann beliebig viele kette projekte laufen lassen". Later: everything must work on project level, not globally.

Until 0.9.4 one machine had one edition, and `kette login`, `update` and `logout` installed the plugins of that edition in the user scope of Claude Code. Every project on the machine saw the same plugins, so a Community project on a licensed machine loaded Enterprise agents, and a machine could not hold an Enterprise and a Community project side by side.

Claude Code (2.1.310, checked in a sandbox HOME) keeps one path per marketplace name for all projects, even when the marketplace is declared in a project: two projects that declare `kette` with different folders repoint each other and the plugins of the first fail to load. It refuses plugin entries that are links leaving the marketplace folder.

## Decision
1. **Instances.** A Kette instance is a folder `~/.kette/instances/<name>/` with `instance.json`: name, edition, optional bundle pin, repos (name and origin URL), members, ticketing (`adapter`, `project`), wallet defaults (`provider`, `project`, `env`), overlays, chain stations. It may be a git clone of an instance repo or a link to one, so the team and Spark agents share it. Any number of instances per machine.
2. **Machine store stays global, everything else per instance or repo.** Global: licence, device ID, bundles (several versions side by side), state (including local checkout paths of instance repos). One licence covers all instances, seats stay per device.
3. **The edition belongs to the instance.** A repo names its instance in `.kette/profile.json` and inherits edition, ticketing, wallet defaults, overlays, stations and the pin; its own values (stack, platform, apps, patterns, flow, overlays) win. `tier` is written to match the instance, also down to Community, because joining an instance is an explicit choice. A Community instance never enables Enterprise plugins or features. An Enterprise instance needs a valid licence.
4. **Plugins per project, never in the user scope.** `.claude/settings.json` switches on the plugins of the project edition and switches off every other Kette plugin; the marketplace path goes into `.claude/settings.local.json` (local scope, git ignored); plugins are installed with project scope. This applies to every repo, with or without instance.
5. **One merged marketplace** (superseded by decision 8 in fix round 1). Because a marketplace name is global in Claude Code, kette builds `~/.kette/bundles/marketplace` (name `kette`) from copies of the plugins of all installed bundles, Enterprise winning for plugins both have. Plugin IDs stay `<plugin>@kette`.
6. **Backward compatible.** A repo without `instance` keeps the ADR-0001 rules for its edition. Plugins an older kette installed in the user scope stay; `kette doctor` names them with the uninstall commands.
7. **Never delete an instance repo.** `kette instance remove` needs `--yes`, unlinks a linked instance and refuses a cloned one.

## Decisions of fix round 1 (coordinator, 2026-10-31)
8. **D2, one marketplace per edition.** A plugin ID resolves to one copy for every project (checked with the real Claude Code: `claude plugin list` reads the same `Read from` folder in every repo), so a shared name `kette` would let a Community repo load the Enterprise copy of `kette-engineering-core`. kette builds `~/.kette/bundles/marketplace-community` (name `kette-community`) only from the Community bundle and `~/.kette/bundles/marketplace-enterprise` (name `kette-enterprise`) only from the Enterprise bundle. Community repos enable `<plugin>@kette-community`, Enterprise repos `<plugin>@kette-enterprise`; every other Kette ID is switched off, also the legacy `<plugin>@kette`. On a licensed machine a Community repo makes kette load the Community bundle. `kette rules`, `.kette/README.md` and `kette doctor` in a Community repo point only to `~/.kette/bundles/community/`. The legacy marketplace `kette` (pointing to `~/.kette/bundles/active`) is no longer declared by kette and stays as it is, so user-scope plugins of older versions keep working until they are removed. When a registered `kette-community` or `kette-enterprise` points to another folder inside `~/.kette` (for example a moved `KETTE_HOME`), kette removes and adds it again; a folder outside `~/.kette` is never touched. `kette logout` removes the marketplace `kette-enterprise` from Claude Code and its folder.
9. **D7, leaving Enterprise.** When a repo joins a Community instance, `tier` goes down and kette removes what it wrote for Enterprise (refined in decision 14): the scope line in the project `.npmrc` and the Enterprise template files it created, which it records with their hash in `.kette/templates.json`. A template file that was changed since is kept and `kette doctor` fails with the files and the fix. A Community project with the Enterprise registry line also fails `kette doctor`.
10. **Fail closed.** When `instance` is set in the profile and the instance is missing, damaged or has an unsafe name, the project counts as Community for every gate (plugins, templates, npm, wallet), never as the edition of the machine. `kette login` and `kette update` warn about such a repo and finish; `kette add`, `kette instance use` and `kette profile --effective` stop with the reason.
11. **QA-01, locks.** Every read-modify-write of machine files runs under a lock: `state.json`, each `instance.json`, the build of each marketplace folder, the unpacking of each bundle version. A lock is a folder `~/.kette/locks/<name>.lock` created atomically (`mkdir`), holding the owner's PID and time. A waiting process retries for up to 30 seconds; a lock whose owner process is gone or that is older than 2 minutes counts as stale and is taken over. Files are written to a temp file of the own process and renamed, so readers never see half a file and no `.tmp` leftovers remain after a crash of another process.
12. **QA-08, repo identity.** A repo is identified by its origin, normalised: user info (tokens, passwords) removed, scheme and host lowercased, `git@host:path`, `ssh://` and `https://` forms of the same repo equal, trailing `.git` and `/` removed. Only the normalised URL without user info is ever written to `instance.json` or printed. A repo without origin is identified by the real path of its git common folder, so a worktree and its main checkout are one repo; two different repos without origin and with the same folder name get distinct names (`web`, `web-2`). One repo belongs to one instance: joining with any checkout (`instance use`, `add --instance`, `add-repo`) removes it from every other instance. Every local checkout is tracked by its path in `state.json` (path to repo name and identity), so `kette doctor --instance` checks each checkout, also a main checkout and its worktrees.

## Decisions of fix round 2 (coordinator, 2026-10-31)
13. **D3, npm.** The npm token stays global per device: the kette block in `~/.npmrc` holds only the `//<registry>/:_authToken=` line. The scope line `@getitdone-gmbh:registry=<kette registry>` is written only into the project `.npmrc` of Enterprise projects, and kette records the exact line in `.kette/templates.json`. `kette login` writes the block without it, `kette update` moves it out of a block from before 0.10. `kette doctor` fails for an Enterprise project without the line (fix `kette add`). In a Community repo npm never resolves the design system packages from the Enterprise registry.
14. **Only what kette wrote.** Leaving Enterprise removes only the scope line kette recorded, or for projects from before the record the line with the kette registry, keeping every other line and the line endings; a foreign registry line (for example GitHub Packages) is never touched. It happens only when a repo joins a Community instance; a repo without an instance behaves as before 0.10. Nothing is deleted through a folder link that leaves the project.
15. **Claude Code from a neutral folder.** `claude plugin marketplace remove` and the user-scope uninstalls run from `~/.kette`: run inside a project, Claude Code also strips the marketplace from that project's committed `.claude/settings.json` (checked with the real Claude Code).
16. **Locks without gaps.** A lock folder appears atomically together with its owner (written into a temp folder of the own process, then renamed into place); a lock without a readable owner is stale at once. A stale lock is taken over only if the folder renamed aside still carries the token that was found stale, otherwise it is put back. Temp folders of dead processes (marketplace builds, bundle unpacking, locks) are removed at the next run.

## Decisions of fix round 3 (coordinator, 2026-10-31)
17. **Lock design (replaces 11 and 16).** The folder lock with rename takeover broke under load: while a holder released, a waiter read no owner, judged the lock stale and moved a live lock aside (4 processes x 100 runs: 3 of 4 gave up after 30 s). The lock is now a file, and three rules make it correct:
    - **Appears whole.** The owner (pid, time, token) is written to a temp file of the own process and hard-linked to the lock path. `link` fails when the path exists, so exactly one process wins and no reader ever sees a half-written owner.
    - **Removed by one claimant per token.** To remove the lock with token T, a process links a claim file named after T (fails when the claim exists), checks that the claim holds T, then unlinks the lock. While the claim exists nobody else can remove that lock, and nobody can create a new one while the path is taken, so the unlink always removes the lock that was checked. The holder releases this way, a waiter removes a stale lock this way. A claim left behind is cleared: after 10 seconds when the lock owner it holds is dead (the holder died while releasing; a live claimant needs microseconds), otherwise after 2 minutes.
    - **Stale only with a readable owner** whose process is gone or which is older than 2 minutes; a missing lock means try again at once, an unreadable one means wait.
    - On Windows, operations that are briefly refused while another process has the file open are retried with a short backoff; a release that keeps failing says so instead of giving up silently.

    Considered: an exclusive-create file (`open` with `wx`) is simpler, but between create and write the owner is empty and cannot be judged; the hard link avoids that window without a second mechanism. OS file locks (`flock`) are not available in Node without a native module. Tested with 4 and 8 processes x 100 runs on one name with a counter, and with a holder killed by SIGKILL, on Linux, macOS and Windows.
18. **CR-NEW-8, D3 migration only with consent.** `kette login` and `kette update` never remove the global scope line of a block from before 0.10 without a yes: in a terminal they show the line and ask (other apps that install `@getitdone-gmbh` packages then need the line in their own `.npmrc`), without a terminal or with `--yes` they keep it and name `kette npm move-scope`. `kette doctor` fails in a Community instance repo where that global line makes the Enterprise registry resolve. Only the marked kette block is ever touched.
19. **QA-28, repoint instead of remove.** A marketplace registration that points to another folder under `~/.kette` is repointed with `claude plugin marketplace add`, which keeps what was installed from it. `marketplace remove` would uninstall its plugins in every project and empty their entries in the user settings (checked with the real Claude Code). The folder of the first 0.10 build is cleaned this way: the legacy `kette` goes back to `~/.kette/bundles/active`.
20. **QA-29, identity in the entry.** A repo without origin carries a hash of its local identity in its `instance.json` entry (`local`, 24 hex characters, no machine path). It is found again without `state.json`, so a kette killed between the two writes cannot put it into two instances; the next successful run repairs the checkout.

## Decisions of fix round 4 (coordinator, 2026-10-31)
21. **KETTE-21, lock follow-ups (amends 17).**
    - **A claim names its claimant (CR-NEW-10).** The claim is no longer a hard link of the lock but the claimant's own file (pid, process start, time), placed the same way as the lock; after placing it, the claimant checks that the lock still holds the token. A claim is cleared only once its claimant is gone, never by age while the claimant lives, so a claimant paused for a long time (a sleeping laptop) never loses its claim and never deletes the lock that follows. A clearer moves the claim aside first and puts back one that a live claimant placed meanwhile. No decision reads ctime any more (NTFS reports a change time that differs from POSIX); ages come from mtime, which the placed temp file sets.
    - **Orphaned claims are swept (CR-NEW-11)** at every lock: claims of claimants that are gone and older than 2 minutes, and unreadable ones of that age.
    - **Drives without hard links (CR-NEW-12).** When `~/.kette` is on such a drive (link fails with ENOTSUP, ENOSYS, EXDEV, EOPNOTSUPP, or EPERM or EISDIR that a probe link confirms), lock and claim are created with an exclusive open and written at once; a reader may see them empty for a moment and waits. If even the exclusive open fails, the message names the folder and says to set `KETTE_HOME` to a folder on a local drive.
    - **Reused pids (CR-NEW-13).** The owner carries the start time of its process. For a lock or claim held longer than 2 seconds whose pid is alive, the start time of that pid from the system (`/proc` on Linux, `ps` on macOS, `Get-Process` on Windows) must match within 2 seconds, otherwise the owner is gone. A lock without a readable owner is removed once its mtime is older than 2 minutes, under a claim, and only if it is still that unchanged file.
    - **Probe and EISDIR (AT-R1, AT-R2).** The probe link of `createAtomic` is named like the temp files of the target (`.<name>.<pid>.<hex>.tmp`), so `sweepTemps` and the ignore pattern catch a leftover; EISDIR from a link counts like EPERM and the probe decides.

    Tested with a claimant stopped for 12 seconds before its unlink while a second process waits, 4 processes x 50 runs with each link error, an unreadable lock, a lock of a reused pid and orphaned claims, on Linux, macOS and Windows.

## Decisions of fix round 5 (coordinator, 2026-10-31)
22. **KETTE-41, lock edge cases (amends 21).**
    - **Start as the system says it (LK-1, LK-2).** The owner keeps the start of its process in the raw form of the system and compares it unchanged: Linux the start ticks of field 22 of `/proc/<pid>/stat` with the boot id from `/proc/sys/kernel/random/boot_id`, macOS the `lstart` text of `ps` with `TZ=UTC` and `LC_ALL=C`. No clock time is computed, so a clock jump, a time zone or a DST hour changes nothing. Windows has no cheap call for the own process (PowerShell would cost a second per kette run), so the owner keeps the start Node stamped and the checker reads the StartTime of the system as UTC FILETIME; both are stamped once at the start, a later clock jump moves neither, and they may differ by 2 seconds.
    - **A claimant checks its claim before the unlink (LK-3).** It reads the claim once more right before it unlinks the lock and removes the claim only if its own content is still there, so a clearer that could not put back a claim it moved never makes two claimants act.
    - **Without hard links, the name must lead to the written file (LK-4).** After the exclusive create and the write, `fstat` of the descriptor and `stat` of the name must show the same file (device and inode or file id); otherwise the lock or claim counts as taken.
    - **No tight loop (LK-5).** A lock that looks gone but is still there (a pending delete on Windows) is tried again after a millisecond.
    - **Async holders renew their lock (LK-6).** `withLockAsync` renews the file time of its lock every 10 seconds while the work runs; a lock counts from the later of its owner time and its file time.

## Alternatives considered
- A marketplace per edition (`kette-community`, `kette-enterprise`): separate by name, but every existing user gets new plugin IDs and the bundles would need renamed manifests. Rejected for now (D2 in docs/instances.md).
- A marketplace per instance, which would also make the bundle pin a real switch: same ID problem, plus one plugin cache per instance. Rejected for now (D6); the pin is a check.
- Keep the user scope and only switch plugins off per project: the user scope would still hold Enterprise plugins on every licensed machine, against the rule "project level, not global".
- Local scope only for the plugin list (`settings.local.json`): nothing committed, but every teammate has to run `kette add` before Claude Code loads anything, and the team does not see which edition a repo uses (D1).
- Remove user-scope plugins of older versions automatically: cleaner, but projects that have not run `kette add` yet would lose their plugins (D5).

## Consequences
- Different repos on one machine can be Community and Enterprise at the same time; a Community repo stays Community after `kette login`.
- `kette login` and `kette update` outside a project change no plugin; each project needs `kette add` (or `kette instance use`) once.
- Claude Code's own registry and cache in `~/.claude/plugins` still change when a project enables plugins; kette cannot avoid that. `~/.npmrc` (npm access per device) and the itdone MCP server of `kette cloud setup` stay in the user scope (D3, D4).
- The profile schema of kette-engineering does not know `instance` yet; the CLI validates the profile without that field until it does (rule gap D8 for the kette-engineering owner).
- This supersedes the part of ADR-0001 that says the edition can only go back to Community by hand: with an instance, `kette instance use` sets it.
